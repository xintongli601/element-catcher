The bundle is a portable component source bundle. It is not an npm package, runnable application, publishing workflow, production-ready scaffold, dependency-complete project, or compile guarantee.

## 2. Product Definition

The user expands one generated-version row in Saved Capture Detail and explicitly chooses an `Export bundle` action. The selected version may be a validated V1 entry, V2 Revision entry, or V2 Regeneration entry. The trusted Side Panel initiates one local browser ZIP download.

There is no automatic bundle export after generation, revision, regeneration, comparison, Preview, local `.tsx` export, fake/development GitHub export, refresh, reopen, capture switch, or navigation.

Milestone 8 Slice 3 connected the accepted pure Bundle V1 writer to one explicit trusted Side Panel download action. It added no dependencies, Manifest changes, CSP changes, IndexedDB writes, backend routes, generated-version contract changes, real Chromium filesystem/download-artifact validation, or final hardening. Slice 4 adds lifecycle hardening coverage and real Chromium download-artifact validation definitions without adding a new implementation slice.

## 3. Bundle V1 Contents

Bundle V1 contains exactly three entries:

```text
README.md
element-catcher.json
src/<ComponentName>.tsx
```

No other entry is allowed in Bundle V1. The bundle contains one selected component only and one source file only. It must not contain screenshots, `CaptureRecord` JSON, metadata sidecars, package files, Tailwind config, build config, lockfiles, generated CSS, tests, examples, deployment files, GitHub files, Figma files, or multiple component files.

## 4. Source Entry Rule

The source entry path is `src/<ComponentName>.tsx`, where `<ComponentName>.tsx` is derived by reusing the accepted Milestone 7A deterministic safe filename helper.

The source entry bytes must exactly equal:

```ts
new TextEncoder().encode(authoritativeEntry.value.code)
```

The bundle exporter must not trim, format, parse, transpile, compile, normalize line endings, insert metadata, add comments, add or remove final newlines, rewrite imports, infer dependencies, or otherwise transform generated source.

Export remains independent from Preview eligibility. A generated version can be bundle-exportable when it is contract-valid even if it is not previewable or not dependency-complete.

## 5. element-catcher.json Contract

`element-catcher.json` is a strict versioned canonical JSON document. It contains only safe bundle information:

```json
{
  "formatVersion": 1,
  "framework": "react",
  "styling": "tailwind",
  "componentName": "<ComponentName>",
  "entryPath": "src/<ComponentName>.tsx"
}
```

Canonical JSON rules:

- UTF-8 encoding.
- Exact object keys above and no unknown keys.
- Deterministic key order exactly as shown.
- Two-space indentation.
- `\n` line endings.
- Exactly one trailing newline.
- Values must be derived from the authoritative validated generated-version entry and the deterministic entry path.

`element-catcher.json` must not contain capture ID, generated-version ID, `sourceCaptureId`, source URL, page title, screenshot, tags, notes, storage keys, timestamps, lineage, provider metadata, backend metadata, GitHub metadata, credentials, tokens, OAuth codes, session information, cookies, browser storage, fingerprints, logical attempt IDs, or local persistence details.

## 6. README Template

`README.md` uses a deterministic fixed template. It must not include capture metadata, generated summaries, approximation notes, tags, source URL, page title, screenshots, IDs, timestamps, backend metadata, provider metadata, or GitHub metadata.

Template:

```markdown
# Element Catcher Component Bundle

This bundle contains component source generated by Element Catcher.

Review the source before use. Dependencies, package.json, Tailwind configuration, build configuration, and application scaffolding are not included.

This bundle is not guaranteed to compile, render correctly, be secure, or be production-ready.
```

README encoding rules:

- UTF-8 encoding.
- `\n` line endings.
- Exactly one trailing newline.

## 7. ZIP Filename Contract

The suggested ZIP filename is derived from the accepted Milestone 7A deterministic safe filename helper by replacing the final `.tsx` extension with `.zip`.

For an authoritative component name `ComponentName`, the natural happy path is:

```text
ComponentName.zip
```

The ZIP filename must not include capture IDs, generated-version IDs, `sourceCaptureId`, source URL, page title, tags, notes, timestamps, random suffixes, GitHub metadata, backend metadata, provider metadata, or local storage keys.

Unexpectedly unsafe component names fail closed and do not produce a ZIP. Duplicate filename handling remains browser-owned.

## 8. Internal Paths and Entry Order

Internal paths are repository-neutral POSIX-style relative paths:

```text
README.md
element-catcher.json
src/<ComponentName>.tsx
```

Required entry order:

1. `README.md`
2. `element-catcher.json`
3. `src/<ComponentName>.tsx`

Internal paths must be bounded, UTF-8 text paths with `/` separators only. They must not include absolute paths, empty segments, `.`, `..`, backslashes, query or fragment characters, NUL, ASCII control characters, Unicode control/format characters, leading slash, trailing slash, or path traversal after normalization.

## 9. Deterministic ZIP32 Wire Profile

Bundle V1 must be byte-stable for repeated exports of the same authoritative generated-version entry and implementation version, apart from browser-owned duplicate download naming outside the ZIP bytes.

Bundle V1 is ZIP32 only. ZIP64, multi-disk archives, encryption, data descriptors, streaming ZIP output, directory entries, local-header extra fields, central-directory extra fields, Unicode path extra fields, file comments, archive comments, and trailing bytes after EOCD are forbidden. Every size, CRC, and offset must be known before local file headers are written. Any value exceeding a ZIP32 field or the stricter Bundle V1 limits fails closed.

Exact archive layout:

1. Local file header for `README.md`, followed immediately by exact README bytes.
2. Local file header for `element-catcher.json`, followed immediately by exact JSON bytes.
3. Local file header for `src/<ComponentName>.tsx`, followed immediately by exact source bytes.
4. Central-directory file headers in the same fixed order.
5. One EOCD record.

No other records or trailing bytes are allowed. All numeric ZIP fields are written little-endian.

Exact ZIP fields:

- Compression method: Store, numeric value `0`.
- General-purpose bit flag: UTF-8 filename flag bit 11 set; data descriptor flag bit 3 unset; encryption flag bit 0 unset; all other unsupported flags unset. Exact bit mask: `0x0800`.
- `version needed to extract`: `20` (`2.0`).
- `version made by`: `0x0314`, meaning Unix host OS value `3` and ZIP version `2.0`.
- Internal file attributes: `0x0000`.
- external attributes: `0x81A40000`, encoding regular file mode `0100644` in the upper 16 bits.
- Local-header extra-field length: `0`.
- Central-directory extra-field length: `0`.
- File-comment length: `0`.
- Archive-comment length: `0`.
- Disk number start: `0`.
- EOCD number of this disk: `0`.
- EOCD disk where central directory starts: `0`.
- Fixed DOS date: `0x0021`, representing `1980-01-01`.
- Fixed DOS time: `0x0000`, representing `00:00:00`.

CRC-32 uses the standard ZIP/IEEE reflected CRC-32 variant: reflected polynomial `0xEDB88320`, initial value `0xFFFFFFFF`, and final XOR `0xFFFFFFFF`. CRC-32 is calculated over the exact uncompressed entry bytes for each entry.

## 10. Limits

Bundle V1 limits:

- Exact file-entry count: `3`.
- Exact directory-entry count: `0`.
- One selected generated version.
- One selected capture owner.
- maximum source-entry UTF-8 bytes: `240,000` bytes.
- maximum UTF-8 bytes for each internal entry path: `128` bytes.
- maximum total uncompressed entry bytes: `241,024` bytes.
- maximum final ZIP bytes: `242,048` bytes.

The source-byte bound covers every currently valid generated source under the existing generated-source contract because `GENERATION_LIMITS.codeCodePoints` is `60,000` Unicode code points and the worst-case UTF-8 expansion is 4 bytes per code point, yielding `240,000` bytes. Existing generation documentation measures string limits in Unicode code points and serialized limits in UTF-8 bytes; Bundle V1 uses the byte form for archive construction. README and `element-catcher.json` are fixed small entries, and the uncompressed and final ZIP limits include conservative headroom for their bytes plus deterministic ZIP32 headers and central-directory records.

If any entry path, entry byte length, total uncompressed byte length, final ZIP byte length, CRC, offset, count, or other numeric ZIP field exceeds these exact limits or any ZIP32 field, export fails closed before download initiation.

## 11. Archive Strategy Decision

Recommended later implementation strategy: a bounded internal uncompressed ZIP writer dedicated to Bundle V1.

Why this is preferred:

- Bundle V1 has only three small, deterministic entries.
- Store-only ZIP avoids compression-level, platform, worker, streaming, and browser variation.
- The implementation can be audited for local-only behavior, fixed metadata, CRC-32, size limits, entry order, UTF-8 filename flags, and byte stability.
- It avoids adding a ZIP dependency, supply-chain review burden, bundle-size growth, CSP questions, and dependency API drift for a narrow export surface.
- It is easy to validate with deterministic artifact-inspection tests.

Rejected for Milestone 8 implementation:

- Reviewed ZIP dependency: potentially useful for broader archive needs, but it adds supply-chain, bundle-size, CSP, maintenance, and token-cost overhead before Bundle V1 proves it needs a general ZIP library. No dependency is approved by this architecture.
- Browser compression streams or another dynamic archive strategy: may reduce bytes, but compression metadata and browser behavior increase determinism and support risk for little value in a three-entry source bundle.
- Server-side ZIP generation: rejected because bundle export is local-first, should not send generated source to backend/provider/OpenAI/GitHub, and should not depend on network or production infrastructure.

## 12. IndexedDB Reread and Stale-State Ownership

Milestone 8 inherits the Milestone 7A authoritative reread boundary:

1. Snapshot the displayed validated generated-version entry.
2. Reread the selected generated-version ID from IndexedDB at export time.
3. Require a valid V1 or V2 entry.
4. Require exact generated-version ID.
5. Require exact `sourceCaptureId`.
6. Require exact displayed-entry equality.
7. Build ZIP entries only from the authoritative reread entry.

Missing, altered, invalid, unsafe, stale, or wrong-capture entries fail closed and do not initiate a download. The implementation must not silently export a newer, older, altered, or wrong-capture entry.

## 13. Side Panel State and Download Lifecycle

Slice 3 added a row-specific `Export bundle` control only inside expanded generated-version details.

Row-local states:

- idle;
- preparing;
- download initiated;
- stale version;
- failed.

State rules:

- State is row-local and ephemeral.
- Same-row duplicate activation is suppressed while preparing or initiating.
- Unrelated generated-version rows are not globally disabled.
- Capture switch, Detail unmount, refresh, and stale asynchronous completion cannot initiate old downloads or restore old success state.
- Leaving Detail clears bundle export UI state.
- Object URLs are owned by one attempt, revoked after initiation at a safe lifecycle point, and revoked on replacement, failure, unmount, and capture switch.
- Temporary anchors are removed even when initiation fails.
- The UI may state that browser download initiation occurred. It must not claim final filesystem write success.

The target mechanism remains the trusted Side Panel Blob/object-URL/temporary-anchor download path. `chrome.downloads` permission is not approved unless later implementation proves the existing mechanism is technically insufficient, not merely inconvenient.

## 14. Privacy and Secret Boundaries

Bundle export must not call backend, provider, OpenAI, GitHub, Figma, source pages, content scripts, service workers, analytics, remote origins, or production infrastructure.

Bundle export must not read or persist credentials, tokens, OAuth codes, refresh tokens, cookies, browser storage, GitHub session data, provider secrets, backend secrets, or authorization headers.

Bundle export must not write IndexedDB, mutate `CaptureRecord`, mutate screenshots, mutate V1/V2 generated-version entries, persist export UI state, create Preview iframes, execute generated source, compile generated source, parse generated source, or infer dependencies.

The ZIP must not include capture metadata, generated-version metadata, source metadata, screenshots, notes, tags, provider metadata, backend metadata, GitHub metadata, credentials, or session information.

## 15. Accessibility

The `Export bundle` control must:

- use a native keyboard-operable button;
- have a version-specific accessible name;
- expose visible safe status text for preparing, initiated, stale, and failed states;
- associate errors with the row-specific control;
- avoid raw IDs and storage details in user-visible messages;
- avoid focus stealing after async completion;
- keep local `.tsx` export, Preview, Comparison, Revision, Regeneration, and fake/development GitHub export controls independently reachable.

## 16. Coexistence

Bundle export is independent from:

- Preview;
- Comparison;
- Revision;
- Regeneration;
- local `.tsx` export;
- fake/development GitHub export;
- backend/provider/OpenAI calls;
- source pages, content scripts, service workers, and remote origins.

Bundle export must not close, open, reorder, reset, or mutate these workflows. It must not automatically run after any of them.
